## 1. 社員の追加・変更・退職

画面には社員を登録する機能がない。`Members` テーブルを AWS のマネジメントコンソール（Web 画面）の DynamoDB から直接編集する（2026-10-09 に担当者が確認）。

| 項目 | 必須 | 内容 |
|---|---|---|
| `memberId` | ○ | 一意の文字列。採番ルールは未確認 |
| `memberName` | ○ | 画面の選択肢に出る名前。伝言の「受電者」「伝言先」にこの文字列がそのまま保存される |
| `displayName` | | 通知メールの差出人表示名 |
| `fromEmail` | | 通知メールの差出人アドレス。SES で検証済みのアドレスに限る |

注意：

- `memberName` を変えると、過去の伝言（旧名で保存済み）とつながらなくなる。一覧の並び順（伝言先に使われた回数）も旧名の分は数えられなくなる。
- 同じ `memberName` が2件あると、差出人情報はどちらか一方しか使われない。

⚠ 追加の例（AWS CLI）：

```
aws dynamodb put-item --table-name Members --item "{\"memberId\":{\"S\":\"<ID>\"},\"memberName\":{\"S\":\"<名前>\"}}"
```

退職者の扱い（削除するか残すか）は未確認。

## 2. 通知が Teams に届かないとき

伝言の登録時、Lambda が SES でメールを送り、Teams チャネルのメールアドレスに届く。

確認する順番：

1. **API の応答が「SUCCESS」か。** エラー時も HTTP 200 で例外名の文字列が返る作りで、**画面はそれでも「完了」画面に進む**（`ConfirmationPage.tsx` は `response.ok` だけを見ている）。失敗は画面では分からない。ブラウザの開発者ツールのコンソールに出る `result=` の行で確認する。
2. **伝言は DynamoDB に保存されているか。** 保存の後にメールを送るので、保存されていて通知だけ来ないなら SES か Teams 側の問題。
3. **Lambda のログ**（CloudWatch Logs、ロググループ `/aws/lambda/message-api-tf`）。送信時に `fromEmail=`・`source=` が出力される。
4. **SES**：差出人アドレスが検証済みか。SES がサンドボックスの場合は、送信先も検証済みである必要がある（サンドボックスかどうかは未確認）。
5. **Teams**：チャネルのメールアドレスが変わっていないか。チャネルの「メールアドレスを取得」で確認し、`terraform/main.tf` の `TEAMS_EMAIL` と比べる。

既定の差出人は前任者個人のアドレスになっている。そのアカウントが無効になると通知が止まる。

## 5. 変更をリリースする

1. ローカルで `npm run dev`（仮データ）で確認する。
2. `npx tsc -b --noEmit` と `npx eslint .` を通す。
3. 画面だけの変更なら、画面をビルドして S3 へ配置する（README「デプロイ」）。⚠
4. API の変更なら、`mvn package` → `terraform plan` で差分を確認 → `terraform apply`。⚠
5. 本番の画面で伝言を1件登録し、Teams に届くこと・一覧に出ることを確認し、テスト用の伝言を削除する。
