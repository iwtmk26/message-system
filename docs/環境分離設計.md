# 本番とテストの環境分離 設計案

2026-10-09 作成。2026-10-09 にコードと `terraform-test/` を作成済み。テスト環境は 2026-10-09 に作成し、画面からの登録とTeamsへの通知まで動作確認済み。

## 目的

テストの操作が本番のデータ・通知に届かないようにする。社内利用のため、費用はほぼかけない。

## 方針

同じ AWS アカウント（東京リージョン）に、テスト用の資源を別名で作る。

| 資源 | 本番（既存） | テスト（新規） |
|---|---|---|
| Lambda | `message-api-tf` | `message-api-test` |
| API Gateway | `message-api-tf` | `message-api-test` |
| DynamoDB | `Messages` / `Members` | `Messages-test` / `Members-test` |
| 通知先（`TEAMS_EMAIL`） | `c9453f82…`（71_伝言メモ） | `371a9bd5…`（99_テスト） |
| 画面（S3・CloudFront） | あり | **作らない**（自分のPCの `npm run dev` で動かす） |
| SnapStart | 有効 | 無効（費用を避ける） |

## 変更点

### 1. API（`Handler.java`）

- テーブル名を環境変数 `MESSAGES_TABLE`・`MEMBERS_TABLE` から読む。未設定のときは今までどおり `Messages`・`Members`。
- 既存の本番は、環境変数を足さなくても動作が変わらない。

### 2. Terraform

- テスト用に新しいフォルダ `terraform-test/` を作る。**本番とは別の state** にする。
- 本番の `terraform/` は変更しない。
- 本番の state がまだ手元にないため、本番を壊さないよう、テスト側は本番の資源を参照しない（名前がぶつからないことを確認済みの別名だけを作る）。
- Lambda の実行ロールは本番と同じ既存ロールを使う想定。ただしそのロールが `Messages-test` などに書き込める権限を持っているかは**未確認**。足りなければテスト用のロールを作る。

### 3. 画面

- API の URL を環境変数 `VITE_API_BASE_URL` から読む（`frontend/src/api.ts`）。
- 接続先ごとに画面の上部に帯を出す。

| 接続先 | 帯 |
|---|---|
| 仮データ（既定の `npm run dev`） | 灰色「テストモード（仮データ）」 |
| テスト用 API | 黄色「テスト環境（99_テスト に通知）」 |
| 本番 API | 赤「本番環境に接続しています」。ただし、本番の画面（CloudFront）を使う人には出さず、本番ビルドを自分のPC（localhost）で開いたときだけ出す |

- 本番の URL は、本番用ビルド（`npm run build`）のときだけ使える。`npm run dev` では、テスト用 API か仮データしか選べないようにする。

## 手順（実装後）

1. `mvn package` で jar を作る。
2. `cd terraform-test` → `terraform plan` で、作られる資源が上の表だけであることを確認。
3. 担当者が `terraform apply` を実行する。
4. `frontend/.env.development.local` にテスト用 API の URL を書き、`npm run dev` で動作を確認する。
5. 登録して「99_テスト」に通知が届くこと、本番の `Messages` に何も増えていないことを確認する。

## 未確認・決める必要があること

- 既存の Lambda 実行ロールの権限
- テスト用の差出人メール（SES で検証済みのアドレスが必要）。本番と同じ `FROM_EMAIL` を使えるかは未確認
- 本番 Lambda に環境変数を足すかどうか（足さなくても動くので、足さない案を既定にする）
